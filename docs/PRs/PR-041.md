# PR-041 — Optional scorer and viewer sound

## Status and branch

One review PR on `agent/pr-041-scoreboard-sounds`, based on merged main `16333fcdd6fe6424315940cba3013b7ea1f75727` (PR-040 / GitHub #41). Richie supplied all seven MP3s and requested this integration. Leave unmerged and undeployed until he tests and approves.

## Behavior

Both boards have a compact speaker button opening Sound settings with Enable sound / Mute sound, Volume and Test sound. Each browser controls its own playback. The default is silent. The preference and volume are remembered locally; after a reload or audio interruption, Enable sound must be tapped again to unlock browser audio. This control is available to all users without changing the Pro preview.

| Accepted action | Audio |
| --- | --- |
| +1 point (either side), or named roster point | point.mp3 |
| General team Ace / Kill / Block | ace.mp3 / kill.mp3 / block.mp3, replacing the point tone |
| Exactly 4 consecutive points (either side) | heating-up.mp3 follows the point/call clip |
| Exactly 7 consecutive points (either side) | on-fire.mp3 follows the point/call clip |
| Timeout start | timeout.mp3 once; the complete supplied clip |

Milestone detection uses the pre-action run, including a set-winning point. Run audio at 4/7 does not change the existing visual heat thresholds. A new action replaces an earlier audio sequence rather than building a backlog. Vibration behavior is untouched; no new vibration feature was added.

## Reliability and limits

A small `lastSound` event (unique ID, scoring timestamp and up to two whitelisted cues) is attached only after a reducer command succeeds. The same event is saved locally and published in the existing complete score transaction/outbox. It adds no separate Firebase message/write and retains existing account ownership, revision and terminal-game fences.

Each board consumes event IDs while muted/inactive as well as while playing. Initial snapshots, duplicate metadata snapshots, style/branding changes, Undo/corrections, expired or future-dated events, reconnect baselines and background catch-up do not replay sounds. Offline scoring plays locally from decoded buffers; offline events are marked local-only to prevent immediate scorer reconnection from sounding an old point on viewers. Viewers receive fresh latest-state sound only, not all missed actions during a disconnection. Undo publishes a null sound event, canceling a pending sequence. End, page departure, mute and backgrounding also stop it.

Audio loading/decoding/playback failures are contained and do not block scoring, local saves or publication. Failed enabling can retry. All seven clips are local assets, predecoded only on enabling, and precached with Workbox for offline availability. There is no external audio/speech service or new npm dependency. `src/public/sounds/README.md` records the user-supplied sources; the earlier search's candidate licenses are not assigned to these recordings.

Browser tests verify decoding, Web Audio scheduling, controls and sync. They cannot establish physical speaker output, iPhone silent-switch behavior, phone browser audio interruptions or gym use. Actual iPhone/Android checks remain Richie's review task. Audio is for a visible board, not background/lock-screen notifications. A viewer with a clock more than five seconds out of sync may suppress sound; scoring remains unaffected.
