# PR-021 — Phase 5 Live Share + Viewer

## Status

Ready for local testing and review.

## Branch

`cursor/phase-5-live-share-feac`

## Purpose

Phase 5 of `docs/SCOREBOARD_REBUILD.md`: anonymous Auth, an unguessable live game ID, scorer stays on `/match`, families watch `/g/:gameId`, on-device QR, presence/viewer count, and a recovery prompt if a live game is still open.

## Scope

- `src/live` adapters for Auth, Firestore, Storage, presence, recovery
- Share Live creates a 128-bit hex game ID (not `game-${Date.now()}`)
- Logos upload to Storage; the game doc stores URLs only
- Point taps send the small score payload
- Viewer route is read-only and pinch-zoomable
- Home asks Resume vs End only after the scorer leaves the app and returns. Keep Live opens Home with a Resume Match button next to Start a Match. After **End Match**, the next **Share Live** mints a new game ID; leftover recovery cannot reopen the ended viewer.
- Chat / reactions stay Phase 6

## Implementation Notes

The scorer URL stays `/match`. The viewer link is `/g/{gameId}` on this Vite app (port 5173). Root `index.html` / `app.js` still use the old `?game=` links until Cutover.

`localhost` must stay in Firebase Auth authorized domains for local live tests.

Ending a live match clears the session epoch, cancels pending score writes, and drops recovery. Share Live after that always creates a new game. New Match while still live keeps the same viewer link.

Firebase init matches the gym app: `getFirestore` and anonymous Auth. Tapping Share Live opens the QR sheet immediately, then writes the game doc. Logo uploads and presence run in the background so a slow Storage write cannot freeze the button.

`connecting` is not used as a locked Share Live state. That lock was added in `33fc7c5` and is what made Share Live appear stuck. Match does not auto-resume a leftover live game on load; Resume Match on Home is the resume path. Share Live after End Match still mints a new game ID.
